# 📚 Sección 3: Scatter-Gather Pattern: Composición de servicios de alto rendimiento

## 🔎 Scatter-Gather Pattern - Introducción

### 🎯 Planteamiento del problema

El patrón **Scatter-Gather** permite enviar una misma solicitud a varios servicios, recopilar sus respuestas y
procesarlas para generar una respuesta al cliente.

A primera vista, puede parecer similar al **Gateway Aggregator Pattern**, que estudiamos en la sección anterior. Ambos
patrones permiten que un servicio consulte a varios microservicios y reúna sus resultados. Sin embargo, se diferencian
principalmente en el tipo de información que solicitan y en cómo utilizan las respuestas.

### ✈️ Ejemplo: aplicación de reserva de vuelos

Imaginemos una aplicación de búsqueda de vuelos, similar a Google Flights o Kayak. El usuario introduce un origen y un
destino, y la aplicación consulta a varias aerolíneas para encontrar vuelos disponibles.

<text color="secondary" size="sm">Diagrama 1. La aplicación consulta varias aerolíneas.</text>

![Aplicación de búsqueda de vuelos](assets/section-03/01.png)

El flujo funciona de la siguiente manera:

1. El usuario solicita vuelos para una ruta determinada.
2. La aplicación envía la misma solicitud a los servicios de distintas aerolíneas, como Frontier, Delta y United. Esta
   etapa se conoce como **Scatter** (dispersión).
3. Cada servicio devuelve los vuelos que tiene disponibles.
4. La aplicación reúne las respuestas, las procesa y devuelve el resultado al usuario. Esta etapa se conoce como
   **Gather** (recopilación).

Una vez recopilados los resultados, la aplicación puede mostrar todos los vuelos disponibles o aplicar una lógica
adicional para seleccionar los más baratos, los más rápidos o los que mejor se ajusten a las preferencias del usuario.

### 🔄 Diferencia entre Gateway Aggregator y Scatter-Gather

Aunque ambos patrones consultan varios servicios y combinan sus respuestas, su propósito es diferente.

![Comparación entre Gateway Aggregator y Scatter-Gather](assets/section-03/02.png)

- **Gateway Aggregator Pattern:** consulta distintos servicios para obtener partes complementarias de la información y
  construir una respuesta completa. Por ejemplo, solicita la carrocería, el motor y las puertas para formar la
  representación de un automóvil.

- **Scatter-Gather Pattern:** consulta varios servicios para obtener respuestas del mismo tipo y después las reúne o
  compara. Por ejemplo, solicita a distintas aerolíneas sus vuelos disponibles para una misma ruta y selecciona la mejor
  opción.

En resumen:

- **Gateway Aggregator:** reúne información complementaria para construir una respuesta.
- **Scatter-Gather:** obtiene respuestas alternativas o equivalentes de varios servicios para reunirlas, compararlas o
  seleccionar las más convenientes.

### 💡 Conclusión

Los servicios de las aerolíneas presentan diferencias tanto en sus interfaces como en la estructura de sus respuestas.
Además, pueden producir errores ocasionales. El patrón Scatter-Gather nos permitirá encapsular estas diferencias,
consultar los servicios para una misma búsqueda, reunir los vuelos obtenidos y procesar sus resultados para devolver una
respuesta unificada al cliente.

## 🧱 Creando DTO

Los servicios de las aerolíneas no devuelven necesariamente la misma estructura de datos. Por ejemplo, Delta y Frontier
incluyen la aerolínea, el origen, el destino, el precio y la fecha, mientras que JetBlue solo devuelve el precio y la
fecha.

Para unificar las respuestas, creamos el DTO `FlightResult`, que representa un vuelo con todos los campos que nuestra
aplicación necesita:

````java
public record FlightResult(String airline,
                           String from,
                           String to,
                           Double price,
                           LocalDate date) {
}
````

Este DTO nos permite representar los vuelos de todas las aerolíneas con una estructura común. En el caso de JetBlue, los
campos airline, from y to pueden completarse con información conocida por nuestra aplicación: la aerolínea consultada y
la ruta solicitada.

Así, aunque las respuestas originales tengan estructuras diferentes, podemos transformarlas a un formato uniforme para
procesarlas y reunirlas mediante el patrón `Scatter-Gather`.

## 🔌 Creando el servicio DeltaClient

Creamos `DeltaClient` para encapsular las llamadas HTTP al servicio externo de Delta mediante `WebClient`.

````java

@Component
public class DeltaClient {

    private final WebClient webClient;

    public DeltaClient(@Value("${sec02.delta.service}") String baseUrl) {
        this.webClient = WebClient.builder()
                .baseUrl(baseUrl)
                .build();
    }

    public Flux<FlightResult> getFlights(String from, String to) {
        return this.webClient
                .get()
                .uri("/{from}/{to}", from, to)
                .retrieve()
                .bodyToFlux(FlightResult.class)
                .onErrorResume(throwable -> Mono.empty());
    }
}
````

#### 🔎 ¿Cómo funciona?

- **Configuración de WebClient:** `@Value("${sec02.delta.service}")` obtiene la URL base desde la configuración de la
  aplicación.
- **Construcción de la solicitud:** se realiza una petición `GET` y se envían `from` y `to` como parámetros de ruta.
- **Procesamiento de la respuesta:** `bodyToFlux(FlightResult.class)` convierte los elementos emitidos por el servicio
  en objetos `FlightResult`, representados como un `Flux`.
- **Manejo de errores:** `onErrorResume(throwable -> Mono.empty())` reemplaza un error por un `Mono` vacío.
  Como el método devuelve un `Flux`, Reactor adapta este resultado a un flujo vacío, sin elementos.

Este último punto permite que un error en Delta no interrumpa necesariamente el procesamiento de los demás servicios.
Sin embargo, el error se oculta y no se distingue de una respuesta sin resultados; más adelante podemos mejorar esta
estrategia.

> **Nota:** `Mono.empty()` devuelve un Mono que completa sin emitir elementos. Aunque el método devuelve un
> `Flux<FlightResult>`, esta alternativa es válida dentro de `onErrorResume()`, ya que ambos tipos son compatibles
> en este contexto. Reactor adapta el publisher alternativo al flujo original, por lo que el resultado observable es
> un flujo vacío, sin vuelos. En el servicio `FrontierClient` utilizamos `Flux.empty()`, que produce el mismo
> resultado, pero devuelve directamente un `Flux`.

## 🔌 Creando el servicio JetBlueClient

Creamos `JetBlueClient` para consumir el servicio externo de JetBlue mediante `WebClient`. A diferencia de Delta y
Frontier, JetBlue solo devuelve el precio y la fecha del vuelo, por lo que debemos completar los demás campos para
utilizar una estructura común: `FlightResult`.

````java

@Component
public class JetBlueClient {

    private static final String JETBLUE = "JETBLUE";
    private final WebClient webClient;

    public JetBlueClient(@Value("${sec02.jetblue.service}") String baseUrl) {
        this.webClient = WebClient.builder()
                .baseUrl(baseUrl)
                .build();
    }

    public Flux<FlightResult> getFlights(String from, String to) {
        return this.webClient
                .get()
                .uri("/{from}/{to}", from, to)
                .retrieve()
                .bodyToFlux(FlightResult.class)
                .map(flight -> this.normalizeResponse(flight, from, to))
                .onErrorResume(throwable -> Mono.empty());
    }

    private FlightResult normalizeResponse(FlightResult result, String from, String to) {
        return new FlightResult(JETBLUE, from, to, result.price(), result.date());
    }
}
````

#### 🔎 ¿Cómo funciona?

- **Configuración:** `@Value` obtiene la URL base desde las propiedades de la aplicación.
- **Consumo del servicio:** se realiza una petición `GET` con el origen y el destino como parámetros de ruta.
- **Conversión de la respuesta:** `bodyToFlux(FlightResult.class)` convierte los datos recibidos en un flujo de
  objetos `FlightResult`.
- **Normalización:** mediante `map()`, se crea una nueva instancia de `FlightResult` que conserva el precio y la fecha
  recibidos, y completa los campos airline, from y to con los valores conocidos por la aplicación.
- **Manejo de errores:** si ocurre un error, `onErrorResume()` devuelve un flujo vacío, evitando que el error se
  propague desde este cliente.

Utilizamos `map()` porque `FlightResult` es un record inmutable. En lugar de modificar el objeto original,
creamos uno nuevo con todos los campos necesarios.

De esta manera, aunque JetBlue devuelva una estructura diferente, `JetBlueClient` entrega los vuelos con el mismo
formato que los demás clientes, facilitando su integración mediante el patrón `Scatter-Gather`.

> **Nota:** `Mono.empty()` devuelve un Mono que completa sin emitir elementos. Aunque el método devuelve un
> `Flux<FlightResult>`, esta alternativa es válida dentro de `onErrorResume()`, ya que ambos tipos son compatibles
> en este contexto. Reactor adapta el publisher alternativo al flujo original, por lo que el resultado observable es
> un flujo vacío, sin vuelos. En el servicio `FrontierClient` utilizamos `Flux.empty()`, que produce el mismo
> resultado, pero devuelve directamente un `Flux`.

## 🔌 Creando el servicio FrontierClient

El servicio `FrontierClient` se encarga de consultar la API de Frontier mediante una solicitud HTTP POST. A diferencia
de Delta y JetBlue, que reciben el origen y el destino como parámetros de la URL, Frontier espera estos datos en el
cuerpo de la solicitud, en formato JSON.

### 1. 📦 DTO para la solicitud

Creamos el record `FrontierRequest` para representar los datos que enviaremos a la API:

````java
public record FrontierRequest(String from, String to) {
}
````

Este record define dos campos:

- **from:** código del aeropuerto de origen.
- **to:** código del aeropuerto de destino.

Spring WebFlux serializa automáticamente el objeto a JSON al utilizarlo con `bodyValue()`.

### 2. 🛠️ Implementación de FrontierClient

````java

@Component
public class FrontierClient {

    private final WebClient webClient;

    public FrontierClient(@Value("${sec02.frontier.service}") String baseUrl) {
        this.webClient = WebClient.builder()
                .baseUrl(baseUrl)
                .build();
    }

    public Flux<FlightResult> getFlights(String from, String to) {
        return this.webClient
                .post()
                .bodyValue(new FrontierRequest(from, to))
                .retrieve()
                .bodyToFlux(FlightResult.class)
                .onErrorResume(throwable -> Flux.empty());
    }
}
````

#### ¿Cómo funciona?

1. **Configuración de WebClient:** el constructor recibe la URL base desde la propiedad `sec02.frontier.service` y crea
   el cliente HTTP.
2. **Solicitud POST:** `post()` establece el método HTTP que requiere la API de Frontier.
3. **Cuerpo de la solicitud:** `bodyValue(new FrontierRequest(from, to))` envía el origen y el destino como un objeto
   JSON.
4. **Recepción de resultados:** `retrieve()` obtiene la respuesta HTTP y `bodyToFlux(FlightResult.class)` convierte el
   cuerpo de la respuesta en un flujo de objetos `FlightResult`.
5. **Manejo de errores:** `onErrorResume(throwable -> Flux.empty())` recupera los errores completando el flujo sin
   emitir vuelos. Esto permite que el proceso Scatter-Gather continúe con los resultados de otras aerolíneas,
   aunque el error queda oculto si no se registra ni se propaga por otro medio.

> **Nota:** `Flux.empty()` devuelve un Flux que completa sin emitir elementos. En los clientes anteriores utilizamos
> `Mono.empty()`, que también completa sin emitir elementos. Ambas alternativas son válidas en `onErrorResume()`
> en este caso y producen el mismo resultado observable; la diferencia es el tipo de publisher que devuelve cada una.

## ⚙️ Configuración de las URL de los servicios

En el archivo `application.properties`, definimos las URL base de los tres servicios externos que consultaremos mediante
WebClient:

````properties
sec02.delta.service=http://localhost:7070/sec02/delta
sec02.frontier.service=http://localhost:7070/sec02/frontier
sec02.jetblue.service=http://localhost:7070/sec02/jetblue
````

Cada propiedad contiene la URL base correspondiente a una aerolínea. Los clientes DeltaClient, FrontierClient y
JetBlueClient obtienen estas direcciones mediante `@Value` al inicializarse.

De esta manera, centralizamos la configuración y evitamos escribir las URL directamente en cada cliente.
